DriftFinder controlled experiment: step by step protocol
=======================================================================

This document describes how to reproduce the DriftFinder experiment and
exactly what happens at every step. The experiment runner
(experiment/run.py) carries out the whole protocol automatically, so you
run a few commands and the runner does the rest. Every result is scored
from the scan output by code. Nothing is typed by hand.

Installation (Docker or native) is covered in README.md. Every command
below is shown in both forms:

  Docker:  driftfinder-experiment <command>
  Native:  python experiment/run.py <command>


=======================================================================
PART 1: BEFORE YOU START
=======================================================================

1. Use a dedicated AWS test account, not a production account. The
   experiment creates and deliberately misconfigures real resources.

2. Use credentials with broad permissions in that account. The simplest
   setup is an IAM user with AdministratorAccess. See "Permissions" in
   README.md for the full list of services.

3. Everything runs in eu-west-1 (Ireland). The region is fixed so that
   every run uses the same AWS environment.

4. Expect a full run to take about 2 hours, including teardown, and to
   cost a few US dollars. A short check (step 3 below) takes about 40
   minutes and costs well under one US dollar.

5. Do not run two experiments at the same time in the same account.
   They use the same resource names and would interfere with each other.
   The preflight check refuses to start if resources from another run
   exist.


=======================================================================
PART 2: RUNNING THE EXPERIMENT
=======================================================================

STEP 1: Start DriftFinder
  Docker: start the container as shown in README.md ("Start
  DriftFinder"). You are now in a shell inside the container.
  Native: activate the virtual environment as shown in README.md.

STEP 2: Run the preflight check
  Docker:  driftfinder-experiment preflight
  Native:  python experiment/run.py preflight

  This creates nothing. It checks:
  - Tool versions. A different Terraform AWS provider or Pulumi AWS
    provider version stops the run, because those write the declared
    state DriftFinder reads. Other differences are reported and recorded.
  - Which AWS account and identity your credentials belong to.
  - Account settings that can affect results: AWS Organizations
    membership (service control policies can block injections), EBS
    default encryption, account-wide S3 Block Public Access and AWS
    Config recorders.
  - Room for three more VPCs in eu-west-1.
  - Leftover resources from an earlier run.

  Continue only when it ends with "Preflight passed".

STEP 3 (recommended): Run a short check first
  Docker:  driftfinder-experiment run --scenarios D1 D4
  Native:  python experiment/run.py run --scenarios D1 D4

  This runs the complete protocol for two scenarios on all three
  environments, then tears everything down. Expected outcome: D1 is FN
  (no drift, see the scenario table) and D4 is TP in all three
  environments, with zero false positives.

STEP 4: Run the full experiment
  Docker:  driftfinder-experiment run
  Native:  python experiment/run.py run

  Type "yes" when asked to confirm, or add --yes for an unattended run.

  Turn off power saving for the run (macOS: Low Power Mode; Windows:
  battery saver). It does not change detection results but slows every
  scan considerably, so recorded scan durations would not be
  representative. The runner records the macOS Low Power Mode setting
  in run.json.

  Keep the computer awake for the whole run. If it sleeps, the run
  pauses until it wakes. For a native run:
    macOS:    caffeinate -ims python experiment/run.py run
    Linux:    systemd-inhibit python experiment/run.py run
    Windows:  set Settings > System > Power & battery > Sleep to
              "Never" for the duration of the run
  For a Docker run, apply the same setting to the computer running
  Docker (on macOS, prefix the docker run command with caffeinate -ims).
  A laptop must also stay plugged in with the lid open.
  The runner prints its progress and writes everything to
  experiment-runs/<run id>/ in your current folder. Results are also
  uploaded to the S3 bucket driftfinder-results-<account id> after
  every step (use --no-upload to keep them local only).

STEP 5: Read the results
  The summary is printed at the end of the run and saved in the run
  folder:
  - results_summary.json  precision, both recall figures and F1 per
                          environment and overall, plus every scenario
                          result
  - outcomes.json         TP, TP*, FN or FN (no drift) per scenario
                          and environment
  - ground_truth.json     every injection, whether it took effect and
                          the finding that matched it
  - scans/ and clean/     every scan DriftFinder produced

STEP 6 (optional): Measure scan performance
  Docker:  driftfinder-experiment benchmark
  Native:  python experiment/run.py benchmark

  Scan duration depends on the computer and network, not only on
  DriftFinder, so it is measured separately from the drift scenarios.
  The benchmark provisions the three environments, runs 26 clean scans
  per environment (interleaved across the environments), writes
  benchmark_summary.json and tears everything down. It takes about 40
  minutes. Turn off power saving first (macOS: System Settings > Battery
  > Low Power Mode > Never; Windows: a non-saver power mode) and keep the
  computer otherwise idle. On macOS the benchmark refuses to start while
  Low Power Mode is on.

IF THE RUN STOPS
  The runner stops on purpose if an environment is not clean after a
  reset, if a scan fails or if an injection fails unexpectedly. The
  reason is printed and saved in run.json.
  - Continue where it stopped:
      Docker:  driftfinder-experiment resume experiment-runs/<run id>
      Native:  python experiment/run.py resume experiment-runs/<run id>
  - Or delete everything it created:
      Docker:  driftfinder-experiment teardown experiment-runs/<run id>
      Native:  python experiment/run.py teardown experiment-runs/<run id>
  After a failure the runner tears down automatically unless you passed
  --keep. If you stop it with Ctrl+C, it leaves the resources running so
  you can resume.

AFTER THE RUN
  The three KMS keys stay in "Pending deletion" for 7 days, the minimum
  AWS allows. This is expected. The results bucket is kept.


=======================================================================
PART 3: WHAT THE RUNNER DOES
=======================================================================

The runner follows these phases in this order. Each completed step is
recorded in progress.json so an interrupted run can resume.

PHASE A: Provision three identical environments
  A1. Terraform: terraform init and terraform apply in a copy of
      experiment/terraform.
  A2. CloudFormation: create the stack driftfinder-experiment-cf from
      experiment/cloudformation/baseline.yaml.
  A3. Pulumi: pulumi up in a copy of experiment/pulumi, using a local
      state backend (no Pulumi account needed).
  Each environment contains one of each of the eight resource types (S3
  bucket, security group, IAM policy, RDS instance, EBS volume,
  CloudTrail trail, VPC, KMS key) in a CIS-compliant starting state.
  The RDS password and Pulumi passphrase are generated randomly for each
  run and never uploaded.

PHASE B: Baseline scans
  DriftFinder scans each environment. Each must report zero findings
  before any drift is injected. If not, the runner retries up to 5 times
  30 seconds apart, then stops.

PHASE C: Drift scenarios
  For each scenario D1 to D24, in order, and for each environment
  (Terraform, then CloudFormation, then Pulumi):
  C1. Inject the change described in the scenario table below and
      record it in ground_truth.json, including whether the change
      actually took effect in AWS.
  C2. Wait 30 seconds for AWS to apply the change.
  C3. Scan with DriftFinder and save the report in scans/.
  C4. Score the scan automatically (see Part 5).
  C5. Reverse the change.
  C6. Scan again. The environment must report zero findings before the
      next scenario starts, so that no scenario is affected by an
      earlier one. If findings remain, the runner retries up to 5 times
      30 seconds apart, then stops. These scans are saved in clean/.

PHASE D: Control scans
  Six scans of the clean environments (C1 and C4 Terraform, C2 and C5
  CloudFormation, C3 and C6 Pulumi). Any finding here is a false
  positive.

PHASE E: Summary
  Precision, recall and F1 are calculated per environment and overall.

PHASE F: Teardown
  All three environments are destroyed, followed by a check that nothing
  was left behind. The result is saved in teardown.json.


=======================================================================
PART 4: THE 24 DRIFT SCENARIOS
=======================================================================

All changes are made through the AWS API with boto3.

CIS: control in CIS AWS Foundations Benchmark v3.0.0, or "none" when
the benchmark has no control for the property.

ID   Resource        Change injected                              Severity  CIS
---  --------------  -------------------------------------------  --------  -----
D1   S3 bucket       Delete the default encryption configuration  HIGH      none
D2   S3 bucket       Turn off all four Block Public Access flags  CRITICAL  2.1.4
D3   S3 bucket       Turn off server access logging               MEDIUM    none
D4   Security group  Allow TCP 22 inbound from 0.0.0.0/0          CRITICAL  5.2
D5   Security group  Allow TCP 3389 inbound from 0.0.0.0/0        CRITICAL  5.2
D6   Security group  Allow all outbound traffic to 0.0.0.0/0      MEDIUM    none
D7   IAM policy      New default version: Action * on Resource *  CRITICAL  1.16
D8   IAM policy      New default version: administrator access    HIGH      1.16
D9   IAM policy      New default version without explicit deny    MEDIUM    none
D10  RDS instance    None: not injectable (immutable)             CRITICAL  2.3.1
D11  RDS instance    Set PubliclyAccessible to true               HIGH      2.3.3
D12  RDS instance    Set backup retention to 0 days               MEDIUM    none
D13  EBS volume      None: not injectable (immutable)             CRITICAL  2.2.1
D14  EBS volume      Create a snapshot of the volume              HIGH      2.2.1
D15  EBS volume      None: not injectable (volume not attached)   MEDIUM    none
D16  CloudTrail      Turn off multi-region logging                HIGH      3.1
D17  CloudTrail      Turn off log file validation                 HIGH      3.2
D18  CloudTrail      Remove the CloudWatch Logs integration       MEDIUM    none
D19  VPC             Delete the VPC flow log                      HIGH      3.7
D20  VPC             Allow TCP 80 inbound on the default SG       CRITICAL  5.4
D21  VPC             Network ACL rule allowing all inbound        MEDIUM    5.1
D22  KMS key         Turn off automatic key rotation              HIGH      3.6
D23  KMS key         Disable the key                              CRITICAL  none
D24  KMS key         Add a key policy statement for principal *   HIGH      none

Scenarios where no drift reaches the account. These are recorded with
"injected": false in ground_truth.json and reported separately:
  D1   AWS applies SSE-S3 encryption to every bucket by default, so the
       bucket stays encrypted. Checked in AWS after the call.
  D10  RDS storage encryption cannot be changed after creation.
  D11  AWS rejects the change because the VPC has no internet gateway
       (a cost decision in the environment design).
  D13  EBS volume encryption cannot be changed after creation.
  D14  AWS encrypts every snapshot of an encrypted volume, so the new
       snapshot is encrypted. Checked in AWS after the call.
  D15  The volume is not attached to an instance, so delete-on-
       termination has no value to change.

Every change is reversed after its scan (phase C5). D10, D13 and D15
make no change and need no reversal.


=======================================================================
PART 5: HOW RESULTS ARE SCORED
=======================================================================

Scoring is done by code from the scan output (README.md, "How results
are scored", has the full rules and the list of derived properties).

  TP   The scan contains a finding on the injected resource and property
       whose actual value matches the injected change.
  TP*  As TP, but DriftFinder did not report the expected CIS control.
  FN   No such finding. "FN (no drift)" when the change did not reach
       the account (see the list in Part 4).
  FP   A finding that is neither the injected property nor one of the
       scenario's derived properties, or any finding in a control scan.

Two recall figures are reported: over all 72 scenario runs, and over the
runs where drift actually reached the account.

The original run reported in the paper followed an earlier, manual
version of this protocol. That version is kept in the git history of
this file.
